## Key Discoveries

### 1. AG-UI Client Architecture

Both .NET and Python implement AG-UI clients that:
- POST requests with messages, tools, and state to AG-UI endpoints
- Parse SSE streams using line-by-line processing
- Convert AG-UI events to framework-native ResponseUpdate types
- Track active messages and tool calls for proper event sequencing

**Key Implementation Components:**
- `client.go` - Main client with Run/RunStream methods
- `http_service.go` - SSE streaming HTTP client (bufio.Scanner)
- `event_parser.go` - JSON to Event parsing
- `response_converter.go` - Event → ResponseUpdate (inverse of existing converter)

### 2. StatefulExecutor Pattern

.NET StatefulExecutor provides:
- Generic typed state (`TState`) with initialization factory
- Automatic state caching (for non-concurrent runs)
- State key management with optional scoping
- Lifecycle hooks: ReadState, QueueStateUpdate, InvokeWithState

**Go Implementation Approach:**
- Wrap any Executor with StatefulExecutorWrapper
- Use generics for type-safe state: `StatefulExecutor[T any]`
- Integrate with CheckpointStore for persistence
- Support optional scope names for shared state

### 3. FileCheckpointStore Design

Both platforms use JSON-based file storage:
- One JSON file per checkpoint
- Atomic writes via temp file + os.Rename (POSIX-safe)
- File naming: `{runId}_{checkpointId}.json`

**Go-Specific Considerations:**
- Use `encoding/json` with struct tags
- In-process mutex for thread safety (not cross-process file locks)
- Optional index.jsonl for fast listing
- LoadLatest() already in Go interface (not in .NET/Python)

### 4. ExecutorOptions Configuration

.NET provides two boolean options with defaults of `true`:
- `AutoSendMessageResult` - Auto-send handler return values as messages
- `AutoYieldOutputResult` - Auto-yield handler return values as outputs

**Integration with Executor Interface:**
- Add optional ExecutorOptions field to ExecutorBase
- Runner checks options after Execute() to auto-send/auto-yield
- Functional options pattern: `WithAutoSend(false)`, `WithAutoYield(false)`

### 5. WorkflowContext Enhancements

**YieldOutput():**
- Creates WorkflowOutputEvent with data and source executor ID
- Added to workflow's event queue for streaming
- Python tracks for ExecutorCompletedEvent

**RequestHalt():**
- Creates internal RequestHaltEvent
- Workflow halts at end of current superstep (graceful)
- Event is filtered from output stream

**State Scopes (optional):**
- State organized by ScopeId (executorId + scopeName)
- Queued updates published at superstep boundaries
- Enables state sharing between executors

### 6. OpenTelemetry Instrumentation

.NET uses comprehensive span hierarchy:
- `workflow.build` - construction phase
- `workflow.run` - root span for execution
- `executor.process` - per-executor spans with links
- `edge_group.process` - message routing
- `message.send` - individual message transmission

**Key Patterns:**
- Span links (not parent-child) for parallel executor execution
- W3C trace context propagation in WorkflowMessage
- Comprehensive attributes: workflow.id, run.id, executor.id, etc.
- Edge delivery status tracking

**Go Integration:**
- Extend existing go/observability package
- Add workflow-specific span names and attributes
- Create WorkflowMetrics struct

* State caching for performance (non-concurrent)

### Scenario 5: WorkflowContext Enhancements

**Description:** Add YieldOutput and RequestHalt methods.

**Requirements:**
* YieldOutput() creates WorkflowOutputEvent
* RequestHalt() sets halt flag for graceful termination
* Outputs() returns queued outputs
* HaltRequested() returns halt status

**Preferred Approach:** Extend existing WorkflowContext

```go
// Add to WorkflowContext struct:
type WorkflowContext struct {
    // ... existing fields ...
    outputs       []WorkflowOutputEvent
    haltRequested bool
}

// WorkflowOutputEvent represents output yielded by an executor.
type WorkflowOutputEvent struct {
    Data     interface{}
    SourceID string
}

// YieldOutput queues an output to be emitted as a workflow event.
func (wc *WorkflowContext) YieldOutput(output interface{}) {
    wc.mu.Lock()
    defer wc.mu.Unlock()
    wc.outputs = append(wc.outputs, WorkflowOutputEvent{
        Data:     output,
        SourceID: wc.executorID,
    })
}

// RequestHalt requests workflow termination at end of current superstep.
func (wc *WorkflowContext) RequestHalt() {
    wc.mu.Lock()
    defer wc.mu.Unlock()
    wc.haltRequested = true
}

// Outputs returns outputs queued during execution.
func (wc *WorkflowContext) Outputs() []WorkflowOutputEvent

// HaltRequested returns true if halt was requested.
func (wc *WorkflowContext) HaltRequested() bool
```

**Impact on runner.go:**
- After Execute(), check `wc.Outputs()` and emit WorkflowOutputEvents
- After superstep, check `wc.HaltRequested()` and break loop

**Effort Estimate:** 0.5 days

### Scenario 6: OpenTelemetry Instrumentation

**Description:** Add tracing and metrics to workflow execution.

**Requirements:**
* Span hierarchy: workflow.run → superstep → executor.process
* Attributes: workflow.id, run.id, executor.id, etc.

* Integration with existing go/observability package

**Preferred Approach:** Extend observability package

// StartWorkflowRunSpan starts a root span for workflow execution.
